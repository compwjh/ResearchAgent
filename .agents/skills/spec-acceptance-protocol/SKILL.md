# Spec Acceptance Protocol

## 触发条件

当一个 Spec 或 Task 已完成实现，需要部署后的运行时验证、API 成功案例、人工验收步骤、准备度评估或“是否可以交给用户验收”的裁决时使用本 Skill。它适用于跨端功能，也适用于只有后端但产品入口仍需真实验证的功能。

不要在以下场景启用本 Skill：只要求单元/集成测试、代码评审、静态契约检查、编写 Spec 初稿，或用户明确只要诊断而不要求验收交付。可在这些场景记录风险，但不能把测试结果当作本 Skill 的验收结论。

## 核心裁决

最终只允许输出以下两种结论之一：

- `READY_FOR_USER`：真实 API E2E 成功、关键产物存在、准备度十项至少通过 9 项，并且没有未解决的 P0/P1。
- `BLOCKED`：任一前置门禁失败、关键证据缺失、自然语言主路径失败、准备度低于 9/10，或存在 P0/P1。必须写清阻塞原因和证据位置，不得编造成功响应、状态或产物，也不得建议用户开始人工验收。

“测试全绿”“表单成功”“直接调用内部函数成功”都不能单独产生 `READY_FOR_USER`。

## 工作边界

- 只验证当前部署版本、当前分支和当前服务地址；不得引用旧端口、旧数据库、旧分支或无法追溯的截图。
- 复用项目已有的真实 API 调用能力（如 `.codebuddy/skills/spec-api-acceptance/SKILL.md` 所述）时，仍须执行本 Skill 的自然语言主路径和准备度门禁。
- 不修改业务代码、数据库数据模型或产品范围来“修”验收失败；发现缺陷时输出 `BLOCKED`，把修复留给实现任务。
- 不要求每个 Task 跑全量回归，也不把人工步骤改写成自动化脚本的替代品。
- 请求/响应记录必须脱敏：不得落盘凭据、Cookie、授权头、个人隐私或隐藏思维链；脱敏后仍要保留足以复核契约的字段。

## 验收流程

### 1. 确认范围和主路径

读取目标 Spec、对应 Task 资料和当前部署说明，确认：

1. 该 Spec 的核心成功场景、成功判据、最终产物和产品入口；
2. 自然语言 Intake 是否属于产品需求；若属于，明确其输入句、会话入口和后续交互；
3. 当前部署版本、服务地址、分支、数据库/模型/外部来源前置条件；
4. 需要保留的失败恢复路径和不在范围内的路径。

若 Spec 仍在初稿阶段，只写“核心成功案例”场景与判据，不填假 ID、假响应或假提示。开发完成后必须把它替换为真实值、真实按钮名称、真实提示和真实结果。

### 2. 真实 API E2E 前置门禁

在人工验收前，先对当前部署服务执行真实 HTTP API 链路：

1. 探活并确认服务、依赖和版本可访问；
2. 从产品允许的创建入口开始，使用新鲜且可追踪的实体 ID；
3. 通过真实 HTTP 请求推动状态机，等待每个异步阶段达到可观察终态；
4. 检查最终业务产物确实生成并可由产品入口查看或下载。

禁止用 mock、fixture、单元测试、测试替身、直接调用 Python/内部函数或只提交完整结构化表单 JSON 代替真实用户路径。表单/结构化 JSON 仅可作为诊断、错误复现或产品明确规定的兜底入口；它不能替代自然语言 Intake 的成功证据。

若自然语言 Intake 属于产品范围，必须用真实聊天/消息入口提交自然语言，并验证服务端解析、会话状态推进和后续产物。自然语言失败而表单成功时，结论必须是 `BLOCKED`，并标注“产品主路径缺陷”；只有 Spec 明确排除自然语言入口时才可不执行这一项，并在证据中写明排除依据。

### 3. 记录真实证据

为每次运行生成不可覆盖的 API 验收 Artifact（失败也要保存），至少包含：

| 字段 | 要求 |
|---|---|
| `spec` / `run_id` | Spec 编号、唯一运行 ID；重试生成新 ID |
| `runtime` | 服务 URL、端口、分支、版本/提交、开始和结束时间 |
| `request` | 方法、路径、必要请求头（脱敏）、真实请求体或自然语言输入 |
| `response` | 每个关键请求的真实 HTTP 状态码、脱敏响应体和错误体 |
| `state_trace` | 实体 ID、状态变化、时间戳、等待条件和最终状态 |
| `artifacts` | 产物 ID、类型、状态、查看/下载路径、内容存在性证据 |
| `result` | `success`/`blocked`、阻塞码、失败原因、重试关系 |

响应可按大小做明确截断，但必须保留状态码、错误码、关键字段和截断说明；不能把真实 JSON 改写成“示意响应”。原始失败证据不能被重试覆盖。缺服务、超时、模型/数据库/外部来源不可用或关键产物缺失时，记录事实并停止，不推测后续成功。

### 4. 生成可独立复现的人工验收案例

人工案例必须让一个没有本次聊天上下文的用户照做。使用当前 UI 的真实文案和真实入口；无法确认的文案写“未验证”，并判为阻塞，不要自行补写。

每一步都必须包含以下六项：

1. **点击/输入**：精确到按钮、标签、菜单、输入框或聊天入口的名称，以及要输入的内容；
2. **点击后提示**：用户应看到的真实文本、状态、卡片或错误提示；
3. **等待**：是否等待、等待什么事件/状态/网络响应；
4. **等待中显示**：等待期间页面展示的阶段、心跳、进度或可接受的静态提示；
5. **下一步**：达到等待条件后用户点击或输入什么；
6. **失败恢复**：若提示超时、冲突、可重试错误或失败，用户如何回到可继续状态；无法恢复时给出阻塞码。

案例还必须列出入口 URL、版本和前置条件、成功判据、失败判据、最终产物查看/下载路径，以及与 API Artifact 的 `run_id`/实体 ID 对照关系。不要只写“等待完成”“检查结果”这类不可操作的句子。

### 5. 十项准备度评估

逐项给出 `PASS`、`FAIL` 或 `N/A`（只有 Spec 明确排除该能力时才允许 `N/A`，并附引用依据）。计分只统计 `PASS`；`N/A` 不得用来掩盖主路径失败。

1. 服务已启动并可访问；
2. 真实 API 创建入口成功；
3. 主路径参数被正确解析（自然语言属于范围时必须验证）；
4. 任务/实体状态从初始态推进；
5. 前端显示处理中提示；
6. 用户知道何时点击或等待；
7. 核心业务产物真实生成；
8. 失败状态有可操作恢复；
9. 页面状态与 API 状态一致；
10. 步骤文档可由无上下文用户复现。

准备度通过条件是 `PASS >= 9/10`、API E2E 为成功、关键产物存在且 P0/P1 为 0。任意 API 失败、自然语言主路径失败或关键产物缺失均直接 `BLOCKED`，即使分数达到 9/10 也不能交付。

## 输出格式

按以下顺序落盘或报告，路径和实际值必须真实存在：

1. API E2E Artifact：请求、响应状态码、关键响应、状态轨迹、实体 ID、产物路径、运行环境和失败证据；
2. Manual Acceptance Case：逐步点击/提示/等待/下一步/失败恢复；
3. Readiness Matrix：十项逐项结果、证据路径、P0/P1 清单；
4. Final Decision：`READY_FOR_USER` 或 `BLOCKED`，以及允许/不允许用户验收的理由。

失败报告必须以 `BLOCKED` 开头或明确标注，列出“已完成到哪一步、真实失败是什么、重试是否允许、需要谁/什么环境解除”。不得用“应该成功”“预计会生成”“可视为通过”等措辞冒充证据。

## 明确不做

- 不把表单路径、内部函数、mock、fixture 或定向测试报告冒充用户成功案例。
- 不在自然语言 Intake 失败时用备用入口掩盖产品缺陷。
- 不伪造 HTTP 状态、响应 JSON、状态转移、产物文件、按钮提示或等待结果。
- 不因准备度达标而忽略 P0/P1、API 失败或关键产物缺失。
- 不在本 Skill 内扩大 Spec 范围、修复业务代码、删除失败证据或自动替用户确认上线。
