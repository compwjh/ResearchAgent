# 复盘：Spec 026 推理档位反馈与首屏响应修复

- 日期：2026-09-12
- 范围：用户报出的三个缺陷（首屏无卡片 / 错误文案误导 / 不支持档位可选）
- 交付：Spec 026 + Task 02–06，真实浏览器与真实后端双证通过

## 一、三个缺陷的真实根因

三个 bug 收敛为**两条**根因，而不是三个独立问题。

### 根因一：无乐观渲染

assistant 卡片的生命周期完全绑在 SSE `meta` 事件上（`frontend/app.js:1825`）。协议建立前，后端还有建会话/消息对、记忆分析入队、读 system rule 等串行工作，叠加本地 Ollama 冷启动 —— 全部暴露为空白等待。

而 Spec 024 §用户体验 要求的「发送后 500ms 内显示模型正在准备」，被实现到了**左侧边栏** `#conversation-status`（`index.html:29`），不在聊天区。合同写了，但落点错了，验收也没抓到。

### 根因二：能力探测脆弱 + 前端不消费能力

四个独立缺陷叠在一起，形成闭环：

1. **探测脆弱**：5 档串行各发一次 `/api/chat`，每档 `timeout=5`；全败即 `raise RuntimeError` → 503。用户看到「模型能力暂时不可用」。
2. **默认档位算错**：`default = "xhigh" if "xhigh" in supported else supported[0]` —— 而 `supported` 按 `off→low→…→xhigh` 顺序构造，故 `supported[0]` **恒等于最低档 `off`**（`ollama.py:97`）。
3. **前端污染禁用输入源**：`loadReasoningOptions` 失败时**编造** `supported=['off']`，把其余四档全灰掉 → 用户看到莫名其妙「只剩关闭」，而不是「能力未知」。
4. **只置灰不校正选中值**：`syncReasoningEffortOptions` 改 `option.disabled`，但从不改 `select.value`；而兜底硬编码是 `xhigh`。于是：默认 xhigh → 模型不支持 → xhigh 被置灰但**仍选中** → 发送 → 409。

**闭环**：第 2 步算出的默认值 → 第 4 步发出去 → 后端 409「当前模型不支持该推理档位」→ 前端第 3 步的硬编码文案把它显示成「连接失败：…请确认后重新发送」。用户被指向网络问题，而真实原因是档位和能力不匹配。

## 二、为什么 Spec 024 的评审没抓到

024 的合同很细（五档、能力映射、event_seq、迁移矩阵都写了），但**只覆盖后端**，前端只规定了「发送后 500ms 内显示准备状态」这种描述性句子，没有规定：

- 前端如何消费 `supported_efforts`（置灰？隐藏？禁用后如何处置选中值？）；
- 错误文案如何按 `code` 分流；
- 探测失败时前端该显示「未知」还是「不支持」。

结论：**跨端合同只写一半，等于没写。** 后端合同再精确，前端不消费就是空转。

## 三、本轮踩到的四个工程问题

### 1. 静态断言是假阳性温床（最重要）

前端契约测试一度 100% 是「从 `app.js` 抽函数体、断言含某字符串」。后果：

- P0-1（非网络错误显示「连接失败」）**测试全绿但运行时错**；
- B12 静态断言可被**死代码**满足（`reason === 'user'` 无调用者仍被断言）；
- 子代理实测：把 `unknown` 伪装成「只支持关闭」，**全前端套件仍 148 passed**。

改进：引入 Node `new Function()` 抽真实函数体执行（`tests/runtime/*.mjs`），以及**真实 Chromium**（Playwright）。**本机 Playwright 一直是装好的**（在 `.venv` 里），但此前多份文档记录为「未安装」，导致 014/015/022/024 多次以「服务未运行/无浏览器」为由把真实交互验收挂 BLOCKED。**这是本轮最大的意外收获。**

### 2. 子代理配置缺陷会静默中断分派

- `frontend-dev` 的 `tools` 白名单原本**没有 `Write`**，agent 一创建测试文件就 `Tool Write not found` 整轮中断；
- `frontend-reviewer` 没有 `TaskOutput`，调一次就中断。

更麻烦的是：**本会话内对已加载 agent 的改动不生效**（缓存），所以「改 `tools` 再重派」也没用，只能在分派指令里显式写明「你没有 Write，新建文件用 Bash heredoc」来绕开。

教训：agent 定义里 `tools` 必须覆盖该角色的全部产出方式（写文件、跑命令、落日志），且**验证方式应是「实际分派一次」而非「看配置」**。

### 3. 子代理可能返回空消息但工作已完成

Task 04、Task 05 两次分派返回空输出。起初误判为「失败」，实际是**已完成但没回传**（`app.js` 已有 +193 行改动、测试文件已建）。

教训：**不信回传，直接查盘**（`git status` + `git diff --stat` + 进展日志目录）。这应写进编排规范。

### 4. 真实模型的探测行为会污染验证结论

排查 P2-1「探测轮数 2 轮」和 S2 失败时，都因为**真实 Ollama 探测结果的瞬时抖动**（模型加载/换模型期间整档超时）而一度误判。最终靠「连续多次重探 + 对比」才把「产品缺陷」与「环境抖动」分开。

## 四、本轮新发现、移交 spec 027 的缺陷

**能力探测结果非确定性**：

| 时刻 | `qwen3.5:9b` 的 `supported_efforts` |
|---|---|
| 首次探测（空闲） | `['off','low','medium','high','xhigh']` |
| 模型切换/加载期间 | `['low','high','xhigh']`（漏 `off` 与 `medium`） |
| 连续 3 次强制重探（空闲） | 三次均全五档 |

- 成因（初步）：探针用 `num_predict:1`，以 `message.thinking` 是否非空判定支持；模型冷启动/换模型时整档 5s 超时 → 该档被误判为不支持。
- 影响：错误结果**被缓存 300 秒**，用户 5 分钟内看到「中档被置灰」；若缓存缺 `off`，用户选「关闭」会被判 409。
- 建议 027 一并承载（027 原计划做并发/预热/超时/持久化），并把「探测结果必须可重复」列为验收点。

## 六、可复用的经验

1. **跨端 bug 必须先跑真实浏览器**，不要用静态断言替代。Playwright 在本仓库可用（`.venv`）。
2. **验收要能区分「环境噪音」与「真回归」**：本次 395 个 pytest error 全部是沙箱临时目录问题，1 个 failed 是既有竞态 —— 两者都必须独立复核，不能照抄上游结论。
3. **「能力未知」与「确实不支持」必须是不同的错误码**（503 vs 409），否则前端无法给出正确文案。
4. **默认值规则要显式写成可测断言**：`['off','low','medium'] → medium` 这种用例能直接抓出 `supported[0]` 这类取错边界的 bug。
5. **红线要在边界表里写死**：024 的「不静默降档」本轮被 B9 提示缺失实际破坏过一次，靠真实浏览器才发现。
