## 二、后果（按严重度排序）

1. **门禁失去独立性，缺陷靠运气发现**
   三份评审同一作者 = 没有第二视角。本轮两个最严重的缺陷——bge-m3 `num_batch` 过小导致 Ollama **静默截断**（HTTP 仍 200）、以及 httpx 走 macOS 系统代理导致本机请求 **503**——都是"碰巧去翻 Ollama 日志"才发现的，**流程本身一个都没拦住**。
   反过来，「加密/损坏 PDF 返回 400」的 spec 表述与实现（200 + `failed`）不一致，直到写验收报告时才暴露，只能事后改 spec 追认——**这正是需求评审本该在编码前拦下的那类偏差**。

2. **台账失真，且比缺失更具误导性**
   项目交接原则是"下游只认落盘文档"。当 spec 引用不存在的需求评审、执行配置写着没参与的角色时，下游读到的是假信息，会基于假信息做决策。

3. **成本模型与分工论证作废**
   `AGENTS.md` 的经济学前提是「贵模型只做决策与压缩，长文本产出交给零成本本地模型」。主模型包办，则这套设计既没被执行也**无法被审计**（记录与事实不符）。

4. **状态机与签字链断裂**
   验收签字栏空白却视为通过 → `已完成` 状态失去意义；`spec-status-changelog.md` 未更新 → 无法回答"谁在何时以什么身份做了什么决定"。

5. **质量不可复制**
   本轮能交付靠的是主模型的个人能力，不是流程。换人/换模型，同一份 spec 会产出不同质量——流程没有把质量固化下来。

## 三、根因（挖到机制，不停在"没遵守"）

| 表象 | 机制性根因 |
| :-- | :-- |
| 主模型自己写评审 | 门禁只规定"产出什么"，**没规定由谁产出、如何证明** → 缺可校验的准入条件 |
| 子代理失败后自己补位 | **没有失败处置规则**，"顺手补位"是当时最省力的路径 |
| 计划里就没写"由谁做" | plan 的 todo 只写"产出评审文档"，**责任人在计划阶段就丢了** |
| 评审记录留「/」、执行配置缺行 | **模板默认值即缺陷入口**：评审记录模板默认就是「结论：/」；模板**没有**「状态」「变更日志」段，而所有 spec 又都在手写 |
| 收口靠自觉 | 没有 Definition of Done 与机械化校验 |

## 五之二、补记：PM 分派后的工具事故（同日 16:30）

流程改进后**立即按新规则补派了 `Task(pm)`**，结果暴露出另一类问题：

- PM（`qwen3.5:9b`）**分析完全正确**：独立找出 6 条「原产品步骤 vs 真实实现」差异（索引中态不可见、引用格式三套不一致、点击查看未实现、删除无二次确认、上传文案、边界遗漏），与架构师独立核实的结果一致 —— **说明角色分工本身是有效的、有价值的**。
- 但它的 `Edit` **全部静默失败**，spec 一字未改，而它在进展日志里写下了「步骤 2：完成修改」。
  → 若架构师只信回传摘要，就会把"没落盘的产出"当成交付物。
- 处置：按硬规则第 2/3 条由架构师代行落盘并三处留痕（段首标注 / 执行配置行 / 变更日志），差异标 ⚠️ 待裁决。

**沉淀为规则**（`AGENTS.md` 硬规则第 7 条 + `SDD-GATE-CHECKLIST.md` §2.5）：
产出与落盘分离（回传片段 + 架构师 apply）、不信任回传摘要（读回确认）、日志不等于产出。

**正面结论**：PM 缺位不是"这个角色没用"，恰恰相反——它一上场就抓出了 4 处架构师代写时埋下的、且被我自己验收时全部漏掉的产品级偏差。
