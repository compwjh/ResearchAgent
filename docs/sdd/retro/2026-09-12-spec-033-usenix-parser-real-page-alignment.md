# 复盘：spec-033 USENIX 解析器与真实页面结构对齐

- 日期：2026-09-12
- 范围：spec-033 全流程（排查 → 建 spec → 三轮实现 → 三道门禁 → 收口）
- 结果：**已完成**，开发主管签字放行

## 一句话结论

**这次事故的本质不是「解析器写错了」，而是「测试 fixture 是理想化的」—— 42 个绿灯测试对应着线上 100% 作者丢失。**
绿灯数量与生产可用性之间没有因果关系，fixture 保真度才是。

## 事故链

| 环节 | 事实 |
|---|---|
| 症状 | 检索结果卡片作者恒为空；任务恒 `partial`/`degraded` |
| 真实根因 | `_Blocks.handle_starttag` 只在 `tag == "p"` 时匹配字段类名，而真实页面把类名放在**外层 `<div>`** |
| 为什么没被测出 | fixture 是手写的理想化 DOM（类名直接写在 `<p>` 上），恰好命中解析器的错误假设 |
| 放大效应 | 只要求 1 个 detail 单元失败，整个检索任务即标 `degraded=True` |
| 数据面影响 | `catalog_papers` 894 行中 894 行 `authors_json` 为空（100%）；摘要仅缺 17 行 |

**教训**：手写 fixture 会不自觉地把「实现的假设」写进测试。**必须至少有一份 fixture 来自真实页面原文**，
并把它当作回归基线，而不是靠人「照着实现补一个看起来像的 HTML」。

## 本次排查中最有价值的一步

用户的第一反应是「是不是另一个 agent 改坏了」（当时工作区确有 spec-032.1 在途改动）。
验证方式：**把对方的改动 `git stash` 掉，用同一份真实页面复现** —— 仍然抛 `USENIX_PARSE_FAILED`。
结论因此从「猜测」变成「证伪」。

**教训**：并发改动的工作区里，「谁改坏的」必须用**对照实验**回答，不能靠 diff 看着像就下结论。
这一步花的时间远少于事后返工。

## 我自己的三个错误（都已纠正）

1. **把不存在的代码写进评审文档**：我把 `degraded` 机制描述为
   `any(item.get("rerank_score") is None for item in ranked)`，但该表达式在 `catalog_search_graph.py` 中**不存在**（实际在 `:203`/`:211`）。
   被 `tester` 独立验收时抓出。
   → **教训**：写进评审/验收文档的每一句「代码事实」都必须当场 `Read` 对应行号，不能凭上下文记忆转述。

2. **缓存重放被当成修复验证**：第一次端到端「通过」时，176 个详情页 fetch unit 仍是 `completed`，
   检索直接重放目录数据、**根本没重新解析**。真正的验证必须**失效缓存 + 强制重抓**。
   → **教训**：验证「解析器修复」时，缓存命中**不是**证据。要在报告里显式区分「缓存重放」与「真实重抓」。

3. **自造假象**：为强制重抓，我只清空了 `catalog_papers.authors_json`，却忘了**作者来源于列表页解析**、
   详情页只回填摘要 → 结果 authors 变成 0/176，一度看起来像新回归。
   失效化**列表页**单元后才恢复 176/176。
   → **教训**：动缓存前先确认「这个字段由哪一层写入」。否则会用自己造的数据污染验收结论。

## 工具环境坑（记录以便复用）

| 现象 | 对策 |
|---|---|
| `find` 在沙箱内被 SIGTERM（退出码 137） | 改用 Glob |
| `grep -n "a\|b"` 交替匹配返回空（静默误导） | 改用 Grep 工具 |
| `deploy/stop.sh` 拒绝停止（内部用 `ps`，沙箱禁用） | `lsof` 取 PID → `kill -TERM` → 删 `deploy/run.pid` |
| 健康检查不是 `/health` 而是 `/api/health` | 先查 `/openapi.json` 确认路径 |
| pytest 需 `env -u PYTHONPATH` + 每次全新 `--basetemp` | 照抄既有约定 |
| **同一文件并行发多个 Edit 会互相覆盖**（其中一个报成功但未落盘） | 同一文件的多次编辑必须**串行**发送，改完 `Read` 回读确认 |

## 收口后补充：存量数据回溯（2026-09-12）

验收时只把 2022 重抓过，全库作者覆盖仍是 **176/894**（2023/2024/2025 共 718 行作者为空）。
**若不回溯，用户在网页上测 2023-2025 会看到作者依然为空，误以为没修好** —— 这是「修了代码但用户仍觉得坏」的典型陷阱。

补做：失效化 2023/2024/2025 的 5 个**列表页** fetch unit 后检索一次（718 条、失败事件 0），全库作者覆盖 → **894/894**。

**这里印证了一条关键结论**：作者来源于**列表页**解析、详情页只回填摘要，
所以存量回溯**只需重抓 7 个列表页**，不必重抓 894 个详情页 —— 成本差两个数量级。
需求评审当时就判断「`metadata_hash` 含 `authors`，修复可自愈、无需数据迁移」，本次实测证实了该判断。

**遗留教训**：验收通过 ≠ 用户看到的效果已修好。凡涉及**存量数据**的修复，验收范围必须包含
「存量是否回溯」这一项，否则绿灯只覆盖新数据。
