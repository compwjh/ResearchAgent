# 复盘：子代理上下文预算决定成败（Spec015 Task13）

- 日期：2026-09-05 ｜ 分支：`feature/spec-015-security-paper-discovery` @ `fe17e71`
- 触发：本轮 B、C 两次分派均出现「产出未收尾」，用户观察到主会话 prompt 持续增长并提出质疑

## 1. 现象（反例）

| 分派 | 耗时 | 工具调用 | 结果 |
|---|---|---|---|
| B（领域模型 + v2 迁移） | ~30 min | 30 | 代码基本完成，但**留下缩进错误**、**结果文档缺失**，需二次分派修复 |
| C（仓储行为 + 并发测试） | ~38 min | 27 | **aborted (code=10003)**，测试写完但**未验证**、**结果文档缺失** |

两次失败形态高度一致：**代码主体完成，收尾步骤（验证/文档）丢失**。

## 2. 根因

不是模型能力问题，而是**上下文预算被前期读取吃满**：

1. 分派 prompt 给出的「只读取」清单过大（spec 章节 + task 文档 + `store.py` 全文 871 行 + domain + 测试），27B 窗口在真正动手前已消耗大半。
2. 主会话自身也存在浪费：task13 文档全量读 2 次、`store.py` 分 6 段读且**段间重叠**、`domain` 读 2 次。工具结果一旦进入上下文就**累积不丢弃**，重复读即重复付费。
3. 子代理虽有独立窗口（其读取不回传主会话），但**它自己的窗口会被耗尽**——这正是「最后一步丢失」的机制。

## 3. 正例（同一模型，48 秒完成）

修复 `upsert_catalog_paper` 缺陷（第 593 行）时改用**极简分派**：

- 直接给出**行号与替换内容**，prompt 明确写「不要读 spec、不要读 store.py 全文」；
- 只做一件事（改 1 行 + 跑测试），不要求写文档。

结果：**48 秒、7 次工具调用、全部验证通过**——与前面 30–38 分钟仍失败的分派形成数量级对比。

## 4. 沉淀为可复用规则

- **R-1｜能给行号就给行号**：凡主 Agent 能自行定位的改动，直接给「文件 + 行号 + 替换内容」，并在 prompt 明写禁止读取的大文件清单。
- **R-2｜一次分派只做一件事**：代码 / 测试 / 文档三者拆开派发，不要打包。
- **R-3｜主会话读取要克制**：同一文件不重复读；大文件用 `offset/limit` 精确取片段且**不重叠**；能用 `grep` 定位就不要全量读。
- **R-4｜aborted ≠ 零产出**：子代理中断后**先查工作树是否已部分写入**（本次 aborted 的分派实际已追加 5 个测试），避免重复劳动。
- **R-5｜纯文档可代行**：结果文档若子代理未产出，且改动**不含任何代码文件**，主 Agent 代行撰写（符合代行例外条件），比再次分派更快更可控。
- **R-6｜验证优先于文档**：若预算紧张，要求子代理「先跑通测试、再写文档」，保证核心交付优先落地。

## 5. 结论

本地 27B 子代理的**瓶颈是上下文预算，不是能力**。控制输入（给行号而非让它读全文）、缩小单次目标（一件事），能把 30 分钟仍失败的任务变成 48 秒成功。后续分派默认按 R-1~R-6 执行。
