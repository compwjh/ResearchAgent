# 复盘：导入状态反馈一致性与 503 伪装问题

- 关联 Spec：spec-019 论文导入状态反馈一致性
- 关联任务：Task03（前端状态单一来源）、Task04（后端错误语义修正）、Task05（评审/部署/复盘）
- 日期：2026-09-09（问题暴露） / 2026-09-10（验收与复盘）
- 作者：跨端验收总控（tester / hy3），主 agent 整理

---

## 0. 背景

用户连续反馈两类"状态矛盾"现象：
1. 点击"添加到知识库"后，状态栏先报"导入服务暂时不可用"，随后又被轮询改写为"导入完成"。
2. 检索 job 仍有效时点击导入，却提示"搜索会话不存在，请重新检索"。

Task02 只读定位到根因 C：后端 `routes_paper.py` 多处 `except Exception` 兜底一律返回 `503 IMPORT_BATCH_UNAVAILABLE`，真实异常被吞；前端状态栏多语义覆写、分组循环中断。Task04 消除 503 兜底、改为可诊断 `424 IMPORT_BATCH_ERROR` + 落日志；Task03 收敛前端状态为单一来源。

---

## 1. 经验一：uvicorn 未启用 --reload，后端修复必须重启才生效

**事实**：本项目 FastAPI 以 `nohup .venv/bin/uvicorn backend.app.main:app --host 127.0.0.1 --port 8002` 启动，**未加 `--reload`**。Task04 改完 `routes_paper.py` 后，首次验收仍观察到旧行为，排查许久才发现是**服务进程仍是改动前的旧代码**——没有重启，改动根本没生效。

**影响**：导致"修复看似无效"，浪费一轮排查，也一度让人怀疑改动方向错误。

**沉淀**
- 任何后端代码改动后，**必须显式重启 8002 服务**再验收；不能假设热加载。
- 验收前先确认进程运行的是最新代码（可比对启动时间与改动时间，或在改动后主动重启）。
- 启动命令统一记到 task 文档（已在 `task-05-review-deploy-retro.md` 固化），禁止触碰 8000 端口另一目录 `/Users/wjh/ResearchAgent` 的进程。
- 若长期迭代，可考虑本地开发显式加 `--reload`，但生产/验收环境以"改完即重启"为纪律。

## 2. 经验二：except Exception 统一 503 兜底会掩盖真实缺陷，错误语义必须可诊断且落日志

**事实**：原 `routes_paper.py` 在 `:697/724/743/762/841`（旧行号）用 `except Exception` 兜底，一律返回 `503 IMPORT_BATCH_UNAVAILABLE`（"批量导入服务暂时不可用"，`retryable=true`）。本次核对确认它至少掩盖了两类真实根因：

- **根因 A：对端复核误杀**。候选解析回退到 catalog job 时，旧逻辑把"会话/候选解析正常但需可行动提示"的情形，与"服务真的挂了"混为一谈，把本应区分的 `SEARCH_NOT_FOUND` / `SEARCH_EXPIRED` / `SEARCH_NOT_READY` 错误语义压扁成一个 503，用户被误导为"服务挂了"并反复重试。
- **根因 B：同步索引结果丢弃**。单篇导入路径在下载/索引环节的 `except Exception` 把"候选已落盘但索引状态未正确回写"等真实失败也包成 503，导致真正失败的导入被当成"服务暂不可用"，失败事实被丢弃、不进入任何可诊断通道。

**影响**：503 兜底把"未预期异常"和"业务可诊断错误"都染成同一个不可行动的文案，既误导用户，也让开发者无法从错误码/日志定位真实缺陷——缺陷长期潜伏。

**沉淀**
- 禁止用单一 `503 IMPORT_BATCH_UNAVAILABLE` 兜底未预期异常。未预期异常应返回带可诊断 `code` 的 `424 IMPORT_BATCH_ERROR`（或显式 500），且 **必须 `logger.exception` 落栈**。
- 业务可诊断错误（检索上下文三态、候选缺失、并发锁等）应有**独立、互斥、文案可区分**的错误码，映射到可行动提示，不与传输层故障混淆。
- `DATABASE_LOCKED` 等确属瞬时冲突的，仍保留 `503 + retryable=true`，但须与"未预期异常"分支严格区分，不得被后者吞掉。
- 任何 `except Exception` 兜底都不得静默吞异常（本次仍发现单篇路径两处 `PAPER_DISCOVERY_STORE_UNAVAILABLE` 未落日志，记 P2-c 遗留）。

## 3. 经验三（建议）：测试 mock 掉被测函数会让真实缺陷长期漏网

**事实（建议项，基于评审交叉核对）**：在导入链路的测试里，若对上传/索引关键路径（如 `run_index_task_sync` 一类同步索引入口）做 mock，测试只验证"调用被触发"，而不验证"真实索引结果是否正确落盘与回写"。本次"同步索引结果丢弃"（根因 B）之所以能长期存在，部分原因在于测试未覆盖真实索引回写路径——mock 让异常分支在测试里"永远不走"，真实缺陷被测试套件放行。

**建议沉淀**
- 对"会决定用户可见结果"的下游调用（下载、索引、落盘、状态回写），优先做**真实集成测试**或至少对"失败/部分成功"分支做不 mock 关键副作用的测试，而非全量 mock。
- 若必须 mock，应补充"mock 抛真实异常"的用例，覆盖 `except` 分支的真实语义（错误码 + 日志），避免 mock 把异常路径变透明。
- 单篇导入新增的 `CANDIDATE_NOT_FOUND` 分支（job 合法已冻结但候选不在结果集）目前缺直接单测，建议补一条断言 404 的用例（记 P2-d 遗留）。

## 4. 其他沉淀

- **前端状态单一来源**：原状态栏被三处（单篇结果/异常/轮询进度）覆写，是"先错后对"的直接原因。Task03 收敛为 `importPhase` + `batches` Map + 终态汇总聚合，且 `directSuccess` 每轮重置、`currentRoundBatchIds` 只统计本轮——验收已确认 P1 修复（grep + node --check + 契约测试 9 passed）。
- **规格与实现一致性**：`CANDIDATE_NOT_FOUND` 状态码后端返回 404，spec 接口表标 400（P2-a）。属标注澄清项，建议后续二选一统一，避免前端 `PAPER_ERROR_TEXT` 对齐困惑。
- **运行时验收纪律**：对"不可直接命中"的状态（`SEARCH_EXPIRED`/`SEARCH_NOT_READY`）采用**可逆临时改库**（UPDATE + `finally` 还原）验证，改库前后比对行数与关键字段，确保零副作用——比直接信任静态分析更可信，也避免污染共享 DB。
