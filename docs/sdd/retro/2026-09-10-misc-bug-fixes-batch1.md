## ① 零碎 bug 用统一容器 spec 承接的流程收益

**现象/做法**：BUG-01（点击无反馈、提示"0 个批次"）与 BUG-02（导入论文 v2 恒为"待索引"）均为不便单独立项的小型缺陷。spec-020 以"现象 → 根因（含文件行号）→ 修复 → 验收"的统一模板把它们收进同一容器，按**批次**记录。

**收益**：
- 避免为每处小修小补重复走"需求评审 → 技术评审 → 立项 → 计划"的完整流程，流程开销显著下降。
- 根因与验收点强绑定（每条 bug 强制带文件:行号），复盘时可逐条追溯，不丢上下文。
- 单端评审与跨端验收可批量化：本批两项共用同一套 skill 流水线（progress-logging / verification-loop / regression-guard），子代理分工清晰。

**边界意识**：容器 spec 明确"明确不做"清单（不改 v1 逻辑、不改上传路径、不新建线程池、不新增/更名 DOM id），防止小修小补蔓延成重构。

## ② 两条入口行为不一致 → UI 表现为"卡住/待索引"，排查须先对比同类入口

**现象**：导入进来的论文在知识库里 v2 永远是"待索引"，用户怀疑"后台在构建但前端没表现"。

**根因**：上传路径（`routes_kb.py:120-132`）在 v1 同步索引后**异步提交 v2**；而导入路径（`application.py` 的 `_default_indexer`）**只建 v1、未提交 v2**。两条入口行为不一致，导致导入论文的 `chunkers.v2.status` 永远停在 `pending`。

**教训**：
- 同类入口（上传 vs 导入）的索引/批任务行为必须对齐，否则差异不会报错、只会在 UI 上表现为"卡住/待索引"这类**静默不一致**，极难从单条路径的单元测试发现。
- 排查此类"看起来没动"的问题时，**第一步应横向对比同类入口**（上传能索引、导入不能），而非在单路径里死磕前端轮询。本次正是通过对比上传路径确认"根本没提交 v2"，而非"提交后失败"。

**正面应用**：修复采用方案 A（与上传对齐）——v1 成功后按 paper_id + 落盘路径异步提交 v2，复用同一单线程池，未从 api 层反向依赖，未新建池，行为回归到与上传一致。

---

## ③ 异步结果若被丢弃会误判失败；本次 v2 刻意不等待、不阻塞，是同一教训的正面应用

**现象/旧教训**：spec-019 的 `_guarded_run` 曾因异步任务结果被丢弃，导致已完成的工作被判失败（任务书亦提示本机 27B 显存不足/超时风险）。

**本次做法**：BUG-02 的 v2 提交**刻意不等待、不阻塞**——`import_paper` 在 v1 同步 `run_index_task_sync` 后立即 `_submit_v2_index`（仅入池即返回），导入响应只看 v1 结果；v2 失败经 `tasks._guarded_run` 兜底写 `STATUS_FAILED` + 真实原因，且**不把导入判定为失败**（`_submit_v2_index` 不向 `_default_indexer` 冒泡异常）。

**为什么是正面应用**：
- 与 spec-019 的教训同源：异步任务的状态必须真实可见、且不能因后台任务未达终态而误伤已成功的主流程。
- 风险降级：即使 27B 显存不足使 v2 失败，导入仍能成功（status=indexed），v2 状态真实置 `failed` 并带原因，可由既有 `reindex` 补救——既不阻塞用户，也不掩盖错误。
- 实测印证：本批导入 `b40e10b975…` 返回 `status=indexed`（11.2s），v2 随后 `indexing(16)→…→indexed(100)` 真实流转；`KB_IMPORT_FAILED`(424) 新语义暴露的论文自身问题也如实可见，而非被 503 掩盖。
