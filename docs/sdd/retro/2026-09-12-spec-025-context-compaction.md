# 复盘：Spec 025 会话上下文压缩与 Token 预算管理

## 结果

占位 Spec → 两轮 Grilling → 技术评审（打回 → 修订 → 复审通过）→ Task02–06 全部完成，Spec 转 `已完成`。

## 做对的

1. **先 grill 再写 spec，省掉一轮返工**：Round 1 直接证伪了"防上下文窗口溢出"这个伪前提（窗口 262144、当前装配约 4k token），把立项理由改成可测的"输入 token 预算 / 首 token 延迟"。若按占位文档直接实施，会做出一个三年内不会触发的功能。
2. **评审打回确实抓到了真问题**：3 个 P0 里最要命的是「装配消费 segments 悬空」——表、worker、摘要都设计了，却没有任何 task 归属"改造装配层去读段"，核心验收会无声落空。这类"链路缺一环"的问题靠自检很难发现。
3. **读时装配 + messages append-only** 让"摘要写错"从数据事故降级为可重放的读时缺陷，也顺带消掉了与 Spec024 数据清理的耦合争议。
4. **统一计量口径**：`estimate_tokens` 唯一实现 + 收敛 `repository.py` 的旧 `*4`，避免 UI 显示 30% 实际已 70% 的两套真相。

## 踩坑与教训

1. **子代理会越界改装配结构**：backend-dev 为了实现"消费段摘要"，把 `build_role_aware_messages` 的 history 从 role 消息搬进了 advisory，改变了既有装配顺序（违反 spec 的"必须复用"条款）。**教训：涉及唯一装配/唯一编排函数的改动，必须在 prompt 里写死"不得改变 X 的结构"，且回传后由架构师 diff 复核关键函数，而不是只看测试通过。**
2. **子代理产出的测试可能是空转的**：两个失败用例里，一个是夹具顺序与生产相反（`list_context_messages` 返回 DESC，测试按升序构造），另一个引用了未定义的 `job`（子代理改到一半被截断）。**教训：子代理回传"N passed"不等于验证有效，必须抽查断言是否真的在验证行为。**
3. **`git stash` 验存量失败是必要动作**：全量回归出现 2 个失败，若不复现就归因，会误判为本次回归。本次用 `git stash push backend/` 在干净树跑同一用例，确认均为存量。
4. **0 倍率模型的代价**：hy3 连续触发 429，Task04 与三份评审的分派均失败，最终由主会话实现与代行评审（已在评审文件标注"代行，非独立评审"）。**教训：分派前要有"限流就地降级为主会话实现"的预案，不要让限流阻塞交付。**
5. **分支未建成**：`git checkout -b feature/spec-025-...` 连续两次因审批超时被取消，实际改动落在 `main`。**教训：需要审批的命令应在任务开始时单独发起，不要夹在长命令里。**
