# 复盘：Spec015 Task15–17 从未被分派（2026-09-06）

## 现象

用户提出「检索时应该有两张来源卡片（USENIX + DBLP 兜底）」，排查后发现该需求（Spec015 **A17 来源进度**）完全没实现：没有 `/api/papers/searches` 系列端点，前端也没有来源卡。而 Spec015 任务表里 Task13–17 全部显示「待执行」，看起来是「一个都没做」。

## 事实核查（归因依据）

| 核查项 | 结果 |
|---|---|
| `.codebuddy/agent-logs/` 中 task15/16/17 相关日志 | **零条**（只有 task13、task14 的日志） |
| git 提交中涉及 task15/16/17 | **零条** |
| `docs/sdd/plans/015/` 计划文档 | **齐备**（task-15/16/17 文档都写好了，含子 agent 分派 prompt） |
| 实际代码进度 | Task13 部分落地（`search_source_progress`、`search_results` 表、`get_search_results_page()`）、Task14 已落地（USENIX 增量目录同步、`/accepted` 只读端点）；Task15/16/17 **未动** |

## 归因结论：主 agent（编排方）的问题，不是子 agent 的锅

子 agent 根本没接到活——Task15/16/17 从未分派，无任何日志与提交，因此不存在「子 agent 没完成任务」。具体编排缺陷有四条：

1. **任务链断档**：Task14 完成后（有提交、有日志），主会话没有继续分派 Task15，链条就停在那里。缺少「一个任务完成 → 立即分派下一任务」的自动推进闭环。
2. **任务表状态未回填**：Task13/14 的代码已落地，但 spec 任务表仍写「待执行」。状态与代码脱节，直接导致本次排查时一度误判为「全部没做」，也让我无法从任务表判断真实进度。
3. **被未确认的新 spec 挤占**：9/5 提出 017 后，主会话转向写 017 spec 与两轮评审修订，占了 9/6 大部分时间；而 017 当时**尚未确认**，本不该挤占已确认的 015 的实施。
4. **停止点没有接续机制**：changelog 记过「按用户要求本轮只落盘文档，暂停代码实现，等待后续安排」，但恢复时没有任何机制提示「015 还有 Task15–17 待办」。

## 规则化改进（立即生效）

1. **任务链推进**：每个任务闭环后，主会话必须**立即**分派下一任务，或显式记录阻塞原因并告知用户；禁止静默断链。
2. **状态与代码同批提交**：代码落地即回填任务表状态与 changelog，不得让任务表长期滞后于代码。
3. **已确认优先**：未确认 spec 的文档工作，不得挤占已确认 spec 的实施时间；需要切换时先向用户说明代价。
4. **交接检查点**：每轮会话结束前，核对「已确认 spec 的下一待执行任务」是否已有分派记录（查 `.codebuddy/agent-logs/`），没有则要么分派、要么明确说明为何暂停。
5. **进度可视化**：任务表状态必须反映真实完成度（进行中的写「实施中（xx%）」，不要一律写「待执行」）。

## 影响

Spec015 的来源进度卡片（A17）与异步搜索链路延后。用户已确定顺序：先完成 017 后端重构 → 全量回归 → 再做 015 Task15/16。
