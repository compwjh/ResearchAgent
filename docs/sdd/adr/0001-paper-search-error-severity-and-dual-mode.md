# 0001 论文检索错误分级与双模式呈现

Status: accepted

用户看到的所有论文检索失败此前被压成一句"论文服务暂时不可用，请稍后重试"：前端错误码映射表未覆盖后端真实返回的码，未命中的一律走兜底文案，既说不清发生了什么，也无法据此排障。我们决定按四档分级呈现错误，并复用页面已有的 `#mode-select`（Normal / Developer）做双模式：两种模式都显示人话文案，仅 Developer 模式额外露出 `code` 与 `request_id`。

## Considered Options

- **维持单档 + 无信息兜底**：零改动，但用户无法判断是该改输入还是该等一会儿，反馈时也无法定位。
- **四档分级，兜底一律附错误码**：排障最直接，但把内部码暴露给所有终端用户，界面变技术化。
- **四档分级，Normal 只给文案、Developer 追加 `code` + `request_id`（选定）**：普通用户读到可行动的中文提示；排障时切到 Developer 截一张图就能按 `request_id` 反查日志。代价是前端要感知模式开关，且同一错误有两套渲染路径需要测试。

四档为：输入校验（参数不合法，指明合法值）、可重试（外部来源临时不可用，带重试按钮）、部分降级（保留结果并说明来源不完整）、阻塞失败（重试无效，说明原因与改法）。

## Consequences

- 前端错误码映射必须覆盖后端全部错误码，新增码时同步补映射，否则又会退回无信息兜底——需要有契约测试守住"映射表覆盖后端码全集"。
- `request_id` 目前后端已在错误响应中返回但前端丢弃，需保留下来才能在 Developer 模式展示。
- 双模式复用既有 `#mode-select`，不新增开关；但论文区此前不读该开关，属于新增依赖。
- 呈现仍受项目脱敏约束：任何模式都不得显示完整请求 URL、异常堆栈或认证信息。
