### Task 文件规范

每个 task 文件应让对应角色无需重新扫描整个项目即可执行，至少写清：

1. **状态与一句话目标**：初始为 `待执行`；只交付一个可独立验收的结果。
2. **背景与前置条件**：引用 spec、README、依赖任务及必要的真实文件，不复制整份 spec。
3. **数据、配置与接口**：只写本任务负责的增量；不涉及时明确写“不适用”。
4. **实施步骤与文件边界**：列出执行顺序、目标文件和完成后的可观察结果；不记录隐藏推理过程。
5. **子代理分派**：写明角色、模型、最小上下文、单次文件范围和回传后的读回校验。
6. **边界与明确不做**：防止 task 在执行时扩大 spec 范围。
7. **验收、风险与回滚**：每条验收标准可执行；失败时说明回退到哪个任务或门禁。
8. **产出物、执行结果与变更日志**：初始写“待执行后填写”，执行后回填真实命令、结果和文件。

task 文件顶部统一提供双向跳转：

```md
> 关联：[spec-NNN](../../specs/NNN-kebab-case.md) ｜ 索引：[README](./README.md)
> 依赖：任务 XX；当前状态：`待执行`
```

### 规范化流程

1. **建档**：架构师创建状态为 `待确认` 的 spec，同时创建 `plans/NNN/README.md` 和任务 02 起的全部 task 文件；禁止在 spec 中留下无法跳转的占位链接。
2. **评审**：开发主管先按完整 spec 做需求/技术评审；评审意见改变范围、接口或验收条件时，先修订 spec，再同步受影响 task。
3. **确认**：只有用户明确确认且前两项评审通过后，spec 才转 `已确认`；所有 task 在此之前保持 `待执行`。
4. **执行**：按依赖顺序逐个执行 task。开始时把 task、README 和 spec 索引中的状态同步为 `进行中`；完成并验证后同步为 `已完成`。发现范围扩大时停止执行，回到 spec 修订与确认。
5. **交接**：角色只以已落盘 spec/task/评审文档为输入；关键决定、命令、测试和失败原因回填 task，不依赖口头上下文。
6. **收口**：全部 task 完成后执行验收、部署和复盘；三份评审真实落盘、开发主管签字、状态台账和引用检查通过后，spec 才能转 `已完成`。
