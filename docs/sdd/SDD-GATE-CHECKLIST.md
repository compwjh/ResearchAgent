# SDD 门禁自检清单（Gate Checklist）

> 用途：把 `AGENTS.md` 的流程规则变成**每道门禁可逐条勾选、事后可审计**的清单。
> 使用方式：主会话（架构师）在**每道门禁结束时**逐条核对，全部勾选才允许进入下一阶段；未勾完继续推进即视为流程违规。
> 本文件是 `AGENTS.md`「三道评审门禁」与「多角色 RACI」的执行细则，冲突时以 `AGENTS.md` 为准。

---

## 0. 为什么需要这份清单

一次需求交付本应走「架构师 → 产品经理 → 开发主管（2 份评审）→ 初级开发 → 测试（验收）→ 开发主管签字」。
若退化成**主模型一人包办**（评审自写、编码自做），而 spec 的「执行配置」仍写着各子代理参与——**记录与事实不符**。
（复盘案例见 `docs/sdd/retro/`。）

由此产生三个具体后果：

1. **门禁沦为橡皮图章**：三份评审同一作者，等于没有独立视角。缺陷只能靠「碰巧发现」，而「实现与 spec 表述不一致」这类偏差往往到验收阶段才暴露，只能事后改 spec 追认。
2. **成本与分工论证作废**：`AGENTS.md` 的核心主张是「贵模型只做决策与上下文压缩，长文本产出交给零成本本地模型」。主模型包办，则这套分工不可执行、不可审计。
3. **台账失真且具误导性**：spec 引用了不存在的评审文档、评审记录结论留「/」。下游按「只认落盘文档」的交接原则读到的是假信息——**错误的文档比缺失的文档更危险**。

根因不是"谁偷懒"，而是**门禁没有可校验的准入条件**：只规定了"要产出什么"，没规定"由谁产出、如何证明、失败了怎么办"。
本清单即为补上这三个缺口。

> `junior-dev` / `tester` 保留为**跨端或归属不确定**时的兼容选项；纯后端优先 `backend-dev`，纯前端优先 `frontend-dev`。

> 模型名以 `ollama list` 实测为准，且必须是不含 `/` 的已注册名（含 `/` 会报 `Subagent model config is invalid`，见 `AGENTS.md`）。

## 2. 门禁清单

### Gate 1 — Spec 编写（架构师 / 主会话）

- [ ] spec 段落齐全：`状态` / 一句话目标 / 数据模型 / 端点接口 / 边界 / 明确不做 / 产品使用步骤 / **执行配置** / **任务计划** / **评审记录** / **变更日志**
- [ ] `状态` 段初始值 = `待确认`
- [ ] 执行配置**五行齐全**（架构师/PM/开发主管/初级开发/测试），每行含**选用模型 + 上下文上限 + 职责**；不适用角色写"不适用（原因）"，**不要整行删除**
- [ ] 架构师行的选用模型填「**自身（当前执行任务的 Agent）**」，**不写死模型代号**
- [ ] spec「任务计划」只含任务标题、文档链接、依赖、状态；详细实施内容已下沉到 `plans/NNN/task-*.md`
- [ ] `plans/NNN/README.md` 与任务 02 起的全部 task 文件已创建；spec、README、task 的双向链接均真实存在，无占位死链接
- [ ] task 初始状态均为 `待执行`，每个文件至少包含目标、前置条件、实施与文件边界、分派、边界/明确不做、验收、风险/回滚、产出与执行结果
- [ ] 评审记录三行均按标准路径预告，并明确写“待评审（未执行）”；不把未产出的文件描述为已完成交付物，不写虚假结论或「结论：/」
- [ ] 自检六条：①边界可测试 ②spec/task 职责分离 ③task 链接真实且依赖无环 ④范围划死 ⑤执行配置完整 ⑥产品步骤映射验收点

### Gate 2 — 需求评审 + 技术评审（**tech-lead 子代理**）

准入：Gate 1 全勾。

- [ ] 用 `Task(subagent_name="tech-lead")` 分派，prompt 中给出：spec 路径、项目硬约束、本次评审重点
- [ ] 产出 `reviews/NNN-requirement-review.md` 与 `reviews/NNN-tech-review.md`，两份**均带结论**（通过/打回）
- [ ] 两份文档头部含 **评审者 / 角色 / 模型 / 分派方式** 四项（用于事后审计"是谁评的"）
- [ ] 评审基于**代码事实**（Grep/Read 真实文件），无"应该没问题"式结论
- [ ] 「通过（附意见）」的意见已沉淀为 spec 的**强制约束**清单

**失败处置（禁止静默补位）**：

1. 子代理调用失败 → **重试 1 次**（本地模型偶发超时属正常，3–8 分钟/次不等，勿误判卡死）；
2. 仍失败 → **换更快的模型**（`qwen3.5:9b`）再试；
3. 仍失败 → 在 spec 变更日志记录「阻塞：tech-lead 评审未执行（原因）」，spec 状态保持 `待确认`，**停下来告知用户**，不自行代写；
4. **确需主模型代行**（用户明确要求/时间紧迫）时必须三处留痕：评审文档头部写「主模型代行（原因）」、spec 评审记录结论后标 `（代行，非独立评审）`、变更日志记一行。

### Gate 3 — 用户确认（状态转 `已确认`）

- [ ] 需求评审与技术评审**均已通过**（或已按上述规则显式标注代行/阻塞）
- [ ] 用户明确表示确认后，spec 状态改 `已确认`，并在 `spec-status-changelog.md` 追加一条

### Gate 4 — 实现（**backend-dev / frontend-dev 专职子代理**；主会话只做最小增量落地与校验）

- [ ] 开始当前任务前，task 文件、`plans/NNN/README.md` 与 spec「任务计划」三处状态已同步为 `进行中`
- [ ] **分派前置（硬卡点）**：本次改动含 `.py` / `.js` / `.html` / `.css` 文件 → **已先发起子代理 Task**（写代码之前发起）。未发起即写代码 = 违规，必须停下。
  - 只改 `backend/**` → `Task(subagent_name="backend-dev")`
  - 只改 `frontend/**` → `Task(subagent_name="frontend-dev")`
  - 跨端改动 → **拆成两次分派**（后端一次、前端一次），不要派一个 agent 通吃
  - 归属不确定 / 暂时无法拆分 → 才用兼容的 `Task(subagent_name="junior-dev")`
- [ ] **任务已拆分**：涉及 ≥3 个文件的改动已拆成「每任务 ≤2 个文件」的子任务；未拆分就整体实现 = 违规。
- [ ] **未代行自查**：含代码文件的改动，确认**没有**用「改动极小 / 上下文在手 / 自己写更快」等理由代行（代行仅允许纯文档改动）。
- [ ] **分派 27B 前先保证显存独占**：`./deploy/stop.sh` 停后端 → 清空 `ollama ps` 里的常驻模型（`keep_alive:0`）→ 再分派（27B 与 bge-m3 并存会 OOM）
- [ ] **防回传截断**：要求子代理「先给完整代码片段、再给说明」，并**把片段同时写进进展日志**（避免回传被截断后一无所有）
- [ ] 用 `Task(subagent_name="backend-dev")` 或 `Task(subagent_name="frontend-dev")` 分派，给出最小上下文（spec 的数据模型/接口/边界/明确不做 + 目标文件路径）
- [ ] 实现严格限制在已确认 spec 范围内；范围扩大 → **先停**，更新 spec 再确认
- [ ] 子代理产出由架构师**读真实文件做最小增量修改**并跑 lint/语法校验，不整文件覆盖
- [ ] 自测：lint 无错 + 测试全绿 + 覆盖率不降低（spec-010 门禁 ≥80%）
- [ ] 当前任务验证通过后，真实命令、结果、产出文件与风险已回填 task，三处任务状态同步为 `已完成`
- [ ] 子代理失败 → 同 Gate 2 的失败处置（重试 → 换模型 → 记录阻塞），**不静默改为自己写整份实现**

### Gate 5 — 验收（**tester 子代理出报告 + tech-lead 签字**）

- [ ] 用 `Task(subagent_name="tester")` 分派，产出 `reviews/NNN-acceptance-review.md`（含通过/不通过结论 + 逐项判定依据）
- [ ] 报告按 spec 的「产品使用步骤 / 边界」逐项判定，附**文件:行**依据
- [ ] **运行时验证**：服务真实启动，跑通主链路（不能只靠单测）
- [ ] 开发主管签字栏填写（tech-lead 或主模型代行时注明）；留空则**不得**把 spec 转 `已完成`
- [ ] 验收不通过 → 退回 Gate 4，不进入部署

## 2.5 子代理产出落地规则

中小模型用 `Edit` 重写大段内容会反复失败，却仍在进展日志里写「已完成修改」——实际文件一字未改。
若架构师只信回传摘要，就会把「没落盘的产出」当成交付物。

**规则**：

1. **产出与落盘分离**：长文本产出（产品步骤、评审报告、大段代码）优先让子代理**把内容回传为片段**，由架构师 `replace_in_file` apply 并校验；确需子代理自行 Edit 时，只让它做**单行/小段**替换。
2. **不信任回传摘要**：子代理说"已修改"后，架构师必须**读回文件确认**（`grep`/`sed` 看目标段），再进入下一门禁。
3. **日志不等于产出**：进展日志记录的是"它做了什么尝试"，不等于"文件被改成了什么"。收口以**文件实际内容**为准。
4. 子代理 Edit 连续失败 ≥2 次 → 转规则 1（回传片段 + 架构师 apply），并在变更日志记录该次工具失败。

## 3. 收口清单（Definition of Done）

全部勾选才算闭环：

- [ ] spec「任务计划」、`plans/NNN/README.md` 与各 task 文件状态一致；所有必需 task 均为 `已完成`
- [ ] spec 状态 → `已完成`（验收未签字则保持 `实施中`）
- [ ] `docs/sdd/spec-status-changelog.md` 已追加本次状态流转条目
- [ ] spec「评审记录」三行的结论**均为真实结论**，无「/」、无占位
- [ ] spec「变更日志」补齐每一行：时间 / 角色（含模型或 agent 名）/ 动作
- [ ] spec 中引用的每个文档路径**真实存在**
- [ ] 复盘已落盘（见 `AGENTS.md`：闭环必须主动复盘，属强制环节）

## 4. 机械化校验命令（收口前后各跑一次）

```bash
# ① spec 中不得残留「结论：/」占位，也不得引用不存在的评审文档
grep -rn "结论：/" docs/sdd/specs/

# ② 每个 spec 引用的 reviews 文件必须真实存在
for f in docs/sdd/specs/*.md; do
  grep -o "reviews/[0-9a-z-]*\.md" "$f" | sort -u | while read -r p; do
    [ -f "docs/sdd/$p" ] || echo "MISSING: $f -> $p"
  done
done

# ③ 执行配置五行齐全，且架构师行不写死模型代号
grep -rn "| 架构师 |" docs/sdd/specs/
#    期望形如：| 架构师 | 自身（当前执行任务的 Agent，不写死模型代号） | 200k | ... |

# ④ spec 中引用的 task 文件必须真实存在
for f in docs/sdd/specs/*.md; do
  grep -o "plans/[0-9][0-9][0-9]/task-[0-9a-z-]*\.md" "$f" | sort -u | while read -r p; do
    [ -f "docs/sdd/$p" ] || echo "MISSING: $f -> $p"
  done
done
```

## 5. 常见退化与对策

| 退化现象 | 后果 | 对策（本文件出处） |
| :-- | :-- | :-- |
| 子代理失败后主模型"顺手补位" | 评审失去独立性，台账与事实不符 | Gate 2/4 失败处置：重试 → 换模型 → 记录阻塞；代行须三处留痕 |
| **让中小模型用 Edit 做大段替换** | 静默失败/反复报错不落盘，子代理却在日志里写"已完成修改" | 见下方「子代理产出落地规则」 |
| 执行配置只填"用得上的角色" | 分工不可审计，PM/测试是否跳过无记录 | Gate 1：五行齐全，不适用写"不适用（原因）" |
| 评审结论留「/」等收口时再补 | 收口时往往忘记，台账长期失真 | Gate 3 + 收口清单 + 校验命令① |
| spec 引用尚未产出的评审文档 | 下游读到假信息 | Gate 1：评审记录初始一律写"待评审（未执行）" |
| 架构师行写模型代号 | 版本迭代后必然失真（历史 17 处误标） | Gate 1：一律写「自身」 |
| 验收报告不签字就转已完成 | 状态机失真，最后一道门禁形同虚设 | Gate 5：签字栏留空则不得转状态 |
| 验收/评审文档与实现不在同一分支提交 | 文档游离在工作树，合并时丢失 | Gate 5 收口：文档随实现一并 commit（`AGENTS.md` Git 规范） |
