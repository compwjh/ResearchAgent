# Spec 039 — API 端到端成功案例与人工验收协议

## 状态

**当前状态：`待人工验收`**

## 一句话目标

让每个 Spec 在交给用户人工验收前，都有一个真实 API 端到端成功案例和一份高可复现的人工验收步骤；自然语言聊天入口属于主验收路径，不能被表单或后端直调替代。

## 背景与问题

- 过去把 API 直接传入完整参数的 smoke 误认为用户可复现的人工成功案例。
- 深度研究的自然语言 Intake 是产品要求，但验收步骤没有明确写出每一步点击、提示、等待和下一步动作。
- 子 Agent 可能只报告定向测试通过，未证明真实服务、真实状态机和最终产物贯通。
- 用户在没有成功案例和明确操作步骤时开始验收，容易把实现缺陷误认为操作问题。

## 数据模型

| 记录 | 必填内容 |
|---|---|
| `ApiAcceptanceRun` | Spec、服务地址、分支、请求、响应状态码、关键响应、产物路径、运行时间、失败原因 |
| `ManualAcceptanceCase` | 前置条件、用户输入、逐步点击、预期提示、等待条件、失败恢复、成功判据 |
| `AcceptanceReadiness` | API E2E 状态、人工案例状态、阻塞项、十项准备度评分、是否允许交给用户 |

## 端点 / 接口

本 Spec 不新增业务 API，定义验收产物和 Skill 接口：

| 动作 | 输入 | 成功返回 | 失败情况 |
|---|---|---|---|
| `run_api_e2e` | 已部署服务、Spec 端点和最小成功参数 | 真实请求/响应 Artifact 与任务 ID | 服务不可用、状态机未贯通、关键产物缺失 |
| `write_manual_case` | API 成功案例、UI 状态机、产品步骤 | 可直接照做的验收文档 | 缺少点击路径、提示或等待条件 |
| `assess_readiness` | 测试、运行时和案例证据 | `ready=true/false` 与评分依据 | 任一 P0/P1 或 API E2E 失败时必须为 false |

## 强制协议

1. Spec 开发完成前必须先跑一个真实 API 端到端成功案例；不能用 mock、单元测试或直接调用内部函数替代。
2. 自然语言聊天入口若属于产品需求，必须作为 API E2E 和人工验收的主路径；表单或直接 JSON 只可用于诊断和兜底。
3. API 成功案例必须落盘真实请求、响应状态码、关键响应、实体 ID、最终状态和产物路径。
4. 人工验收案例必须逐步写明：点击哪个按钮、点击后显示什么、是否等待、等待时显示什么、下一步怎么做、失败如何恢复。
5. 交给用户前，准备度评分至少达到 90%（十项检查至少九项通过），且不得有未解决的 P0/P1、API E2E 失败或关键产物缺失。
6. 若自然语言 Intake 失败，不能把表单成功当作主路径成功；必须记录为产品路径缺陷并阻止人工验收交付，除非 Spec 明确把自然语言入口排除在范围外。
7. 每个 Spec 的验收文档必须包含一个“核心成功案例”，开发结束后补齐具体值和真实提示；Spec 初稿只需描述场景和判据。

## 验收准备度十项检查

1. 服务启动并可访问；
2. 真实 API 创建入口成功；
3. 主路径参数被正确解析；
4. 任务状态从初始态推进；
5. 前端显示处理中提示；
6. 用户知道何时需要点击或等待；
7. 核心业务产物真实生成；
8. 失败状态有可操作恢复；
9. 页面状态与 API 状态一致；
10. 步骤文档可由未读上下文的用户复现。

## 边界与失败场景

- 服务、模型、数据库或外部来源不可用时，API E2E 不得伪造成功。
- 研究任务长时间运行时，必须显示阶段、心跳或明确等待提示，不能只显示静态“处理中”。
- 只通过表单、内部函数、fixture 或 mock 的案例不能作为用户验收成功案例。
- 成功案例必须使用当前部署版本，不能引用旧端口、旧数据库或旧分支结果。
- 失败重试不得覆盖原始失败证据；应记录新的运行 ID 和结果。

## 明确不做

- 不要求每个 Task 都跑全量回归；Task 仍只跑定向测试。
- 不把人工验收步骤写成自动化脚本的替代品。
- 不承诺数学意义上的真实成功概率；“90%”是交付前证据准备度门槛。
- 不因验收协议新增业务领域、研究来源或 UI 功能。

## 产品使用步骤（初稿）

开发完成后，每个 Spec 至少提供一个核心成功案例：

1. 打开当前部署地址并确认版本/健康状态。
2. 新建会话，在聊天框使用自然语言提交完整需求；若产品要求结构化 Intake，明确每个字段的填写位置。
3. 根据页面提示补充参数；每次提交后记录页面显示的状态和下一步动作。
4. 观察计划、审批、执行、产物生成等阶段，记录等待提示和预计等待条件。
5. 检查最终产物内容、来源、状态和下载/查看路径。
6. 额外执行一个失败或恢复场景，验证用户能根据提示继续操作。

开发结束时，Task14/最终验收文档必须把上述步骤替换为真实按钮名称、真实提示文本、真实等待条件和真实结果。
