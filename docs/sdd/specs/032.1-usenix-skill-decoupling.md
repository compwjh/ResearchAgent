## 一句话目标

把 USENIX 论文获取链路明确拆成 **Skill（编排层）** 与 **Tool（执行层）**：新增两个只写编排协议的
Skill（旧 Skill 保留并标记遗留），同时在确定性代码中补齐 presentation 详情页摘要抓取与
`fetch_paper_detail` Tool，使论文结果卡片能展示真实摘要而非 `abstract_status: missing`。

## 背景与问题

1. **详情页摘要从未抓取（功能缺陷）**：年度 accepted 列表页实际不含摘要（`catalog_search_graph.py:775-778`
   注释自认 "USENIX listing pages carry no abstract"）；真正有摘要的是每篇论文的 presentation 详情页
   （如 `https://www.usenix.org/conference/usenixsecurity24/presentation/zhang-qingzhao`），
   但 `parse_usenix_detail()`（`usenix_paper_parser.py:139-163`）只取 title/authors/year/PDF，**不取 abstract**，
   导致摘要全空、只能以 `abstract_status: missing` 兜底。
2. **Skill 混入非领域内容（架构问题）**：`usenix-accepted-papers` 与 `usenix-paper-catalog-search`
   两份 SKILL.md 里塞进了研发分派纪律（引用**并不存在的** `junior-dev`、每次 2 文件 150 行、回传字段清单）、
   研发台账回填（Task、`.sdd/runtime/task-ledger.sqlite3`）、Git 禁止项（reset/stash/clean/自动 push/合并 main），
   以及对 spec015 研发过程文档的引用。这些属于主 Agent 的调度规则，不属于「如何获取论文数据」。

## 术语表（本次确立，全项目一致）

| 术语 | 定义 | 不得混淆为 |
|---|---|---|
| **Skill（编排层）** | 供 LLM Agent 读取的协议文档，只决定「抓哪些单元、何时抓详情页摘要、DBLP 补字段时机、单源失败如何降级、何时才允许碰 PDF」 | 抓取脚本；研发 task 文档；可执行的编排引擎 |
| **Tool（执行层）** | 后端确定性原子动作（HTTP 抓取 / HTML 解析 / 缓存 / provenance），由代码注册、白名单校验后执行 | Skill 的一个章节；prompt 片段 |
| **Source** | 论文来源（usenix / dblp，后续 ndss / ccs / sp），带 `authority_rank` | 一个 HTTP 接口 |
| **FetchUnit** | Source 下的持久化抓取单元（年 / cycle / track / 详情页），带租约与内容哈希，已完成单元跳过网络 | 一次 HTTP 请求 |
| **Presentation 详情页** | `https://www.usenix.org/conference/<conf>/presentation/<slug>`，唯一可靠的官方摘要来源 | 列表页；PDF 页 |
| **Abstract Provenance** | 摘要的字段级来源记录；高权威（USENIX 官方）不得被低权威（DBLP）覆盖 | DOI provenance |

> **关键澄清（防止后续误设计）**：LangGraph 当前的 `sync_usenix ∥ sync_dblp` 是**代码级并行 fan-out**
> （`catalog_search_graph.py:251-279`），与 LLM 和 Skill 无关。加入新会议 = 新增 source 节点（代码），
> **不加 Skill**。Skill 只在「对话点名」或「未来 spec027 Research Agent」链路被 LLM 读取。

### 两套 Skill 目录的定位（易混淆，务必分清）

| 目录 | 加载者 | 用途 | 本文涉及 |
|---|---|---|---|
| `.agents/skills/` | **产品后端** `backend/app/skills/scanner.py` | 产品运行时的编排协议，供 http://127.0.0.1:8000 的对话链路读取 | 任务 02–05 的四份 Skill 都在这里 |
| `.codebuddy/skills/` | **IDE 的 CodeBuddy** | 研发流程 Skill，供本地会话的 agent 读取 | 任务 08 |

**实测教训**：本地会话要求「使用 `usenix-catalog-orchestration` 下载论文」时，
模型回答「没有这个 skill，也没有联网工具」——因为它只加载 `.codebuddy/skills/`，
**看不到 `.agents/skills/`**；且 Skill 只是文档，本地会话缺少可执行的工具。

让本地会话具备该能力的正确做法：**在 `.codebuddy/skills/` 建立带 `scripts/` 的 Skill，
用 Bash 调用本地产品服务的既有 API**，而不是把 `.agents/skills/` 复制过去
（复制过去仍无工具，照样干不了活）。详见任务 08。

## 数据模型

| 字段 / 对象 | 类型 | 约束 |
|---|---|---|
| `CatalogPaper.abstract` | str | **已存在字段**，本次由详情页填充；**fill-if-missing 语义**——仅填补缺失，不覆盖列表页已有摘要 |
| `abstract_status` | enum | `available` / `missing`，语义不变（修复后多数由 missing 转 available） |
| FetchUnit `unit_id`（详情页） | str | 形如 `usenix\|{conference_id}\|{year}\|{cycle}\|detail:{slug}`；沿用 `ensure_fetch_unit` / `acquire_fetch_unit` / `release_lease` |

| `fetch_paper_detail` Tool | ToolEntry | 注册进 `backend/app/skills/registry.py`，entry 必须指向真实可定位代码入口 |

## 端点 / 接口

| 动作 | 输入 | 成功返回 | 失败 |
|---|---|---|---|
| `fetch_paper_detail`（新增 Tool） | `catalog_paper_id` 或已验证的 presentation URL | 标题/作者/摘要/关键词/PDF 链接 | 非 allowlist URL → 拒绝；未注册/已禁用 → 拒绝 |
| `GET /api/papers/searches`（既有） | — | **契约不变**，仅摘要字段有值 | 不变 |

> 本 spec **不新增 HTTP 路由**；`fetch_paper_detail` 是 Agent 可调用的 Tool，不对外暴露端点。

## 边界（每条之后会变成一条测试）

- 详情页 URL 必须通过 `_safe_url(..., presentation=True)`：仅 `https` + `www.usenix.org` +
  路径匹配 `^/conference/[^/]+/presentation/[^/]+/?$`，且不得含 query / fragment / 用户名密码。
- 非 allowlist URL、任意根 URL、客户端传入的裸 URL → **一律拒绝**，不接受任意 URL 入参。
- 列表页已有摘要时，详情页**不覆盖**（fill-if-missing）。
- 详情页仍无摘要 → 保留 `abstract_status: missing`，不改变既有空值语义。
- 内容哈希命中 → 跳过网络；限流（`_before_request` / `_rate_limit`）必须生效，禁止整年重抓。
- 详情页抓取失败 → 该单元置 `failed`（可重试），**不得**影响其余论文，不得使整个 job failed。
- USENIX 摘要属高权威，不得被 DBLP 覆盖（既有 `merged.abstract or paper.abstract` 保持不变）。
- 搜索/目录同步阶段**仍然禁止** GET/HEAD/Range PDF、魔数/页数检查或调用 `paper_download.py`。

## 产品使用步骤

- 步骤 1：用户在论文检索页输入研究方向与年份，发起搜索。
- 步骤 2：后端按既有九节点链路同步 USENIX 与 DBLP；USENIX 同步时**自动补抓每篇论文的详情页摘要**。
- 步骤 3：结果卡片展示标题、作者、**摘要**；此前摘要恒为「缺失」，修复后正常展示。
- 验收场景：搜索任一年份 → 结果中至少大部分论文卡片显示非空摘要，且 `abstract_status` 为 `available`；
  重复搜索同一年份 → 命中缓存，`completed` 单元不重复发起详情页网络请求。

## 端到端验收证据（对话链路实测）

验收标准：**在对话里点名 USENIX Skill，能真正获取到论文数据（含摘要）**。

实测（真实服务 + 真实 Ollama + 真实 usenix.org）：

```
POST /api/chat
{"question": "使用 usenix-catalog-orchestration 技能检索 vehicular perception
             相关的 2024 年 USENIX Security 论文，并补齐最相关那篇的摘要",
 "model": "qwen3.8:27b-mlx"}

SSE 事件序列：meta → intent → token → done
```

- `intent` 事件：`{"skill": "usenix-catalog-orchestration", "source": "rule", "confidence": 1.0}`
  —— 编排层（新 Skill）被规则正确命中。
- 模型随后自行编排：调用 `search_paper_catalog` → 命中 10 篇真实 USENIX Security 2024 候选；
  对摘要缺失的第 1 篇调用 `fetch_paper_detail` → **补齐官方摘要**。
- 返回摘要与官方详情页原文**逐字一致**
  （`On Data Fabrication in Collaborative Vehicular Perception: Attacks and Countermeasures`）。
- 边界未被突破：全程未触碰 PDF，模型主动提示切换到 `usenix-download-orchestration`。

> **本轮端到端暴露并修复的缺陷**：`_search_catalog` 的 `output` 原先只拼标题、不带详情页 URL，
> 导致模型虽能检索、却拿不到地址去调 `fetch_paper_detail`（模型遵守「不得猜测 URL」的硬边界而拒绝补齐）。
> 该缺陷**只有端到端才暴露得出来**，单元测试无法覆盖——已修复为输出每篇候选的
> `article_url`（回退 `source_page_url`），并新增定向测试。
