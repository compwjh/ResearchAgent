## 强制约束（须固化进 spec / task）

- **R1 当前服务前置门禁**：遵守用户最新指示，在 spec-014 进入实施前先对当前未提交代码执行首页、`/api/health` 或 `/api/kb/health` 以及全量测试验证并落盘结果；当前服务不能运行则暂停 spec-014，不以回滚 spec-013 作为修复手段。
- **R2 产品步骤补齐**：用户确认后、首个实现任务开始前，由 PM 把“启动服务 → 查看健康状态 → 原方式提问 → 自动重排 → 停服后 RRF 降级”写成逐步用户旅程，并逐项映射 A1–A12。
- **R3 冻结质量集**：不少于 10 个问题的文本、目标片段标识和相关性判定必须在首次查看 rerank 排名之前落盘；不得删除失败问题或事后改变标签来通过 A8。
- **R4 动态回归基线**：最终全量测试数量不得低于 `max(253, spec-013 最终验收通过数)`，覆盖率不得低于 80%，且 spec-011/012/013 的既有验收用例不得被跳过。
- **R5 脏工作树保护**：不得在当前工作树执行 `git reset --hard`、`git clean`、`git stash`、覆盖式 checkout 或批量复制。独立 worktree 从明确 commit 创建后，只复制/应用 spec-014 自身文档和后续 spec-014 改动；spec-013 仅在其形成明确 commit 后按 Task 08 集成。
- **R6 流程模板一致性**：spec 的评审记录按最新模板写出三份标准路径并标注真实状态，自检更新为六条；执行配置使用的 `qwen3.8:27b-mlx` 在实现前补录到 `MODEL_REGISTRY.md`，并保留 `ollama list` 实测证据。

## 风险定级：中

功能本身是可插拔、无数据迁移的低侵入变更；风险主要来自真实 rerank 运行时尚需 Go/No-Go、进程生命周期，以及 spec-013 未提交工作与 spec-014 并行。上述风险均有明确门禁和隔离手段，不构成方案打回。
