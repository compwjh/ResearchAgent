## 二、问题清单

### MEDIUM-1 详情续跑阶段忽略 `years`，跨年度放大外部请求

- 文件：`backend/app/paper_discovery/infrastructure/usenix_publication_source.py:764-797`（`_resume_detail_units`），
  调用点 `:509-510`
- 问题：`_resume_detail_units` 用 `reader([conference_id], None, index_status=None)`（`:778` / `:781`）
  读取**该会议全部年份**的目录行，完全忽略 `sync_usenix_units(..., years)` 的 `years` 入参。
- 实证：预置 2025 年一篇无摘要论文，**只搜索 2024**，第二次运行（listing 已缓存）实际发起
  `GET /conference/usenixsecurity25/presentation/old-2025` 并写入其摘要。即「用户搜 2024，
  后端却改了 2025 的数据」。
- 影响：外部请求量与 embedding 成本按「全部年份 × 每年数百篇」放大；写入用户未查询年份的数据，
  违反按年份请求的语义。
- 最小修复：把 `years` 透传进 `_resume_detail_units`，并将读取改为
  `reader([conference_id], list(years), index_status=None)`（`_sync_detail_units` 的
  `_page_paper_ids(conference_id)` 同理建议收窄到本次 `years`）。

### MEDIUM-2 Tool 路径每次新建 `UsenixAcceptedSource`，限流与缓存均失效

- 文件：`backend/app/skills/tool_dispatch.py:200`
- 问题：`UsenixAcceptedSource()` 每次调用都新建实例，导致
  - `_before_request` 的节流状态 `_next_request_at`（`usenix_publication_source.py:353-359`）与
    `self._cache`（`:138`）随实例丢弃；
  - `_fetch_detail`（`:861-874`）本身也不读写 `self._cache`。
- 实证：连续 3 次（每次新建实例）调用 `fetch_paper_detail` → 3 次网络请求，`sleep` 记录为空
  （限流未触发）；同实例连续两次同 URL → 2 次请求（无缓存复用）。
- 影响：spec 边界「限流（`_before_request` / `_rate_limit`）必须生效，禁止整年重抓」在 Tool 路径
  未落实；编排器若循环调用可造成对 usenix.org 的高频请求。
- 最小修复：改为复用进程级单例（如模块级 `_DETAIL_SOURCE = UsenixAcceptedSource()`，或经既有
  service/容器注入），并在 `_fetch_detail` 内补 `self._cached(self._cache, ("text", url))` 复用
  既有 `_get_text` 缓存语义。

### MEDIUM-3 `_catalog_metadata_hash` 与 `_persist_paper` 的 hash 字段集不一致，可能导致重复 embedding

- 文件：`usenix_publication_source.py:80-97`（`_catalog_metadata_hash`，`page_unit_id` 固定为 `None`）
  vs `:596-606`（`_persist_paper`，`page_unit_id` 为真实 listing `unit_id`）
- 问题：同一篇论文的 `metadata_hash` 在「详情回填」与「listing 重抓」两条路径下必然不同，
  即使摘要内容一致，listing 重抓会把 `index_status` 重置为 `pending` → 触发不必要的重新 embedding。
- 影响：成本型问题（重抓 listing 时全页论文重新嵌入），不产生错误数据。
- 最小修复：两条路径共用同一份 metadata 构造（例如抽 `_catalog_metadata(paper, abstract, page_unit_id)`
  并统一 `page_unit_id` 取值），使「摘要未变」时 hash 稳定。

### LOW-1 `_detail_url_ok` 未 strip / 拒绝显式 `:443`

- 文件：`usenix_publication_source.py:663-675`
- 问题：`" https://.../alpha "` 会返回带尾随空格的 path（非 None），`:443` 端口被拒（比
  `validate_url` 更严）。前者会生成带空格的 `unit_id`（`tool_dispatch` 已 `.strip()` 兜底，
  但 `fetch_paper_detail` 直接入参时不会）。
- 影响：无安全后果；仅 unit_id 可能出现空格导致的缓存未命中。
- 最小修复：入口统一 `url.strip()` 后再校验。

### LOW-2 `result.detail_failed` 无生产消费者，摘要补齐失败对用户不可见

- 文件：`usenix_publication_source.py:56-60`、`:901`
- 问题：`detail_failed` 仅测试引用，生产代码（progress / job / API 载荷）不读取；失败只能通过
  `USENIX_DETAIL_FAILED` 事件观测。
- 影响：符合 spec「不降级 job」要求，但用户侧无法感知「摘要补齐失败」。
- 建议：作为已知限制接受；若需可见性，可在 `SearchSourceProgress` 增加计数（不改 search 契约）。

## 三、可接受的已知限制

1. **详情单元 `content_hash` 不参与「变更重抓」判断**：一旦 `completed` 即永久跳过网络，与 listing
   单元行为一致（`:502`）：若 USENIX 事后更新摘要，本地不会自动刷新。属既有设计一致性，非本次回归。
2. **`handle_startendtag` 新实现使自闭合标签（如 `<meta .../>`）也进入既有解析路径**：
   `usenix_paper_parser.py:95-101`。实测为行为改善（更完整采集），且对无斜杠真实页面无影响；
   因属既有路径行为变更，记录于此备案。
3. **`%2f` 形式的编码斜杠可通过 `_detail_url_ok`**（如 `.../presentation/alpha%2f..%2f..`）：
   目标主机仍是 `www.usenix.org`，Drupal 解析后不构成路径穿越/SSRF；写入目标由 `catalog_paper_id`
   决定，不会串写他人摘要。

## 强制约束清单（后续改动必须遵守）

1. 详情阶段（含续跑与 Tool 路径）的一切目录读取，**必须按本次请求的 `years` 收窄**，不得跨年度抓取。
2. 任何新增的 USENIX 出站请求入口，**必须复用同一实例**（共享 `_before_request` 节流与 `self._cache`），
   禁止在每次调用处 `UsenixAcceptedSource()` 现场构造。
3. `CatalogPaper.metadata_hash` 的构造**只允许一份实现**；新增/修改字段时必须同步
   `_persist_paper` 与详情回填两条路径，避免无谓的重新 embedding。
4. 详情页 URL 校验**只能经 `_detail_url_ok` + `validate_url`**；不得在任何新入口直接使用入参 URL 发请求。
5. 搜索/目录同步链路**永久禁止**触碰 PDF（`_get_pdf` / `download_candidate` / `paper_download.py` /
   魔数 / 页数检查）。
6. `result.failed` 的含义（listing 召回失败 → 驱动 `partial`/`degraded`）不得改变；
   详情失败只能进 `detail_failed`。
7. 摘要写入必须保持 fill-if-missing，且缺失时保留空值并标注 `abstract_status: missing`，禁止编造。
