## 一、评审范围与依据

依据 SDD 需求评审四问逐项核验：① 目标是否清晰；② 范围是否可测；③ 边界与「明确不做」是否完整；④ 产品使用步骤是否可操作。

## 二、逐项核验

### 1. 目标是否清晰 —— 通过
- 一句话目标（spec L13）明确：以 `create_chat_model()` 为唯一收口点按模型名分发 provider，使对话/KB/文章/技能「无缝支持线上模型」；模型库按端侧/线上分组；线上 Key/地址/清单在 `.env` 静态声明；`/api/health` 的 `models` 保持不变，新增 `GET /api/models`。
- 背景与现状表（L17-28）用「现状 / 位置 / 影响」三列把 6 处关键接缝讲清，目标—手段对应明确，无歧义。

### 2. 范围是否可测 —— 通过
- 「边界」15 条（L156-170）每条均可直接映射为用例（spec 自检①亦自证）。
- 「数据模型」三张表（`.env` 解析规则 / 线上注册表项 / API 返回体）字段、类型、约束齐全，可被契约测试断言。
- 端点契约（L96-130）给出成功返回 JSON 示例与错误情况，`GET /api/models?probe=1` 语义清晰。
- 轻量探测参数表（L145-152）数值明确（max_tokens=1、8s 单次、60s 缓存、15s 总上限）。

### 3. 边界与「明确不做」是否完整 —— 通过
- 边界 15 条覆盖：空配置、缺 Key、地址不可达、格式非法、大小写、id 冲突、全空、reasoning-options 不报 404、探测失败仍 200、缓存、别名、XSS、当前模型恢复、删除回退、direct 路由回退。
- 「明确不做」10 条（L172-183）划清：UI 不填 Key、embedding/reranker 不接线上、不支持线上思考档位/不解析 reasoning_content、不改 `/api/health`、不做负载均衡/计费/限流/自动下载、不补端侧 size 元数据、不做搜索排序筛选、不自动探测未声明模型、不改 `MODEL_REGISTRY.md`、不改 `get_available_models()` 的 `List[str]` 返回值。
- 两者闭合，AI 自由发挥空间被有效约束。

### 4. 产品使用步骤是否可操作 —— 通过
- 产品使用步骤 7 步（L187-193）+ 验收场景 A–E（L195-199）可操作、可映射到边界 1/2/3/4 与边界 14。
