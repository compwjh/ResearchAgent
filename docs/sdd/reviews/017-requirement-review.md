# Spec017 需求评审：后端限界上下文彻底重构

> 关联：[Spec017](../specs/017-backend-bounded-context-modularization.md) ｜ 任务索引：[Plan 017](../plans/017/README.md)
>
> 评审角色：开发主管 ｜ 评审日期：2026-09-05 ｜ 结论：**打回**

## 评审范围与证据

- 已核对 Spec017 的目标、边界、明确不做、执行配置和任务依赖。
- 已核对现有单一路由的 30 个公开操作，以及前端实际调用的健康检查、文章助手、论文发现和知识库接口。
- 已核对当前环境变量与持久化设置入口：`ARTICLE_SETTINGS_JSON`、`ARTICLE_*`、`PAPER_DISCOVERY_*`、`OLLAMA_*`、`KB_*`、`QDRANT_PATH` 及默认数据目录。

## 结论依据

重构目标、业务边界和“不留内部兼容层”的意图清晰，且任务 02 → 03 → 04/05/06 → 07 的依赖顺序可执行。保留对外 HTTP、前端 JSON、环境变量和用户数据的原则也正确。

但当前规范尚不能作为可独立验收的需求基线，不能证明“保持不变”覆盖了所有真实公开行为。尤其现有 API 含未由前端直接调用、但已公开的别名与操作（例如 `/papers/import-batches/*`、`/papers/browser-health`、批次取消、文章下载探测/计划和下载 Skill），其中部分本身带有历史兼容语义。Spec 同时要求不保留旧内部兼容层，必须明确该要求不允许删除既有外部端点或改变其响应。

因此本次需求评审结论为**打回**；以下项目补齐并重新评审后，才可进入用户确认。

## 必改项

1. 在 Spec 的“端点 / 接口”或等价的明确验收附录中，写入现有 OpenAPI 的完整基线来源与判定规则：全部路径、HTTP 方法、路径参数、请求/响应 schema、状态码、错误 payload、响应媒体类型（特别是 `/api/kb/ask` 的流式响应）均须不变。必须明确保留所有当前公开别名；“不保留兼容层”只适用于 Python 内部 import/实现路径，不适用于 HTTP 表面。
2. 把环境与数据兼容性变成可验证的矩阵：列出当前生效的 `ARTICLE_*`、`PAPER_DISCOVERY_*`、`OLLAMA_*`、`KB_*`、`QDRANT_PATH` 等变量及默认数据位置；定义配置 JSON 与环境变量同时存在时的优先级。对 `data/article_settings.json` 必须给出拆分后的读取映射、写回的字段保留规则与冲突验收样例。
3. 在确认前补齐“产品使用步骤”和可执行验收场景，至少覆盖：健康检查；文章设置读取/保存、任务创建、轮询和人工登录恢复；会议查询/启停、论文检索、批量导入、重试、浏览器登录与恢复；知识库上传、轮询、重建、删除和 SSE 问答；聊天。每项需写出成功可观察结果及一个保持原错误码/错误体的失败场景。
4. 明确旧目录清理的判定边界。为 `services/`、顶层 `domain/`、`agents/`、`graphs/` 中每个现有业务文件建立迁移分类（移动至哪个模块、合并、删除或明确保留为 `platform`），并规定检查范围是项目源代码、测试、脚本和文档中的哪几类 import。避免“迁移范围内”成为无法判定的例外。

## 风险与验收关注点

- 把路由拆分误解为可以清除 HTTP 别名，会让已有自动化或外部调用直接失效，即使当前前端不调用该别名。
- `ArticleSettings` 拆分时若采用整文件序列化，容易覆盖另一个限界上下文尚未加载的配置字段；需用真实旧 JSON 的双模块字段样例回归验证。
- API 路由不能直接创建仓储、浏览器、Qdrant 或 HTTP 客户端；除结构扫描外，需要至少一条能够在 CI 执行的边界测试，防止重构后回流。
- OpenAPI 路径快照不足以发现 JSON 字段、状态码、SSE 媒体类型与错误体变化，故需使用前述完整契约断言。

## 重新评审准入条件

- Spec 的评审记录将本次结论保留为真实“打回”结果；修订后由开发主管重新执行需求评审。
